Chapter 4 · LLM Advanced

Mixture of experts: many FFNs, few used per token

Mixtral, DeepSeek-V3, Qwen3-MoE, Kimi K2, Llama 4 and OLMoE replace the dense FFN with E parallel FFNs and a router that sends each token to k of them.

12 sections · needs: transformer blocks, GPT-2 from scratch, scaling laws, distributed training (ZeRO/FSDP, tensor/pipeline), Llama 3

01Intuition

Sparse models store E FFNs but compute through only k

A dense model with N parameters pays about 2N FLOPs per token, forever, including at inference. A sparse layer holds E FFNs ("experts") and a router sends each token to k of them (typically 1, 2 or 8).

Why it works: FFNs act like key-value memories, and a Python token and a French token rarely need the same memories. Conditional computation grows the memory without growing per-token arithmetic.

03A short history

Four papers built the modern MoE recipe

Switch halves router compute, communication and expert compute against top-2, and quality held. GShard also made expert parallelism expressible with SPMD sharding annotations.

04Capacity factor

Capacity caps tokens per expert and overflow rides the residual

A larger CF drops fewer tokens but pads memory and FLOPs. Dropless routing (MegaBlocks, OLMoE; DeepSeek-V3 reports no drops) uses grouped GEMM kernels with variable tokens per expert. Balance then costs speed, not quality: an overloaded expert is a slow GPU.

05Load-balancing loss

The product f·P gives a differentiable push toward uniform load

We want each expert to receive about 1/E of the tokens. Variance of the load f is useless: f comes from an argmax and has zero gradient almost everywhere. P is differentiable but is not what we care about. Multiply them.

  1. Gradient points the right way. Overloaded experts (large f) get their probability pushed down hardest, and softmax pushes the others up.
  2. Minimum at uniform routing. If f ≈ P, the sum is about Σf², minimized at f = 1/E. With the E factor the minimum is 1, so a healthy run logs about α.
  3. Cheap. Two reductions over the batch.

The cost: it competes with language modeling. A large α forces uniform routing, even to worse experts. That tension motivates the bias method in section 08.

06Router z-loss

The z-loss shrinks router logits without changing the routing

Logits can drift large. Softmax saturates, and in bf16 an exponential near 100 keeps very few significant bits. ST-MoE found this a major source of instability.

Softmax ignores a constant shift of all logits, so routing decisions are untouched while numerics stay healthy. PaLM used the same trick on its output softmax.

07Expert parallelism

Expert parallelism turns every MoE layer into two all-to-alls

With E experts on D devices, each device holds E/D of them. Attention and other dense parts still use data and tensor parallelism. EP is a fourth axis beside ZeRO/FSDP, tensor and pipeline parallelism.

All-to-all gets no ring tricks. Its cost is bounded by bisection bandwidth and hurts across nodes, where InfiniBand is several times slower than NVLink. So:

  • Load balance is speed: the layer ends when the busiest device ends.
  • DeepSeek-V3 limits each token to experts on at most 4 nodes and overlaps communication with compute (DualPipe).
  • Top-k is a systems choice too.

10Do experts specialize?

Experts specialize, but mostly by syntax and not by topic

Safe summary: experts specialize along axes the model finds useful, often lexical or syntactic, which map poorly onto human topic labels. Specialization grows with finer-grained experts.

11Code

A reference MoE layer fits in about 60 lines

Readable, not fast: it loops over experts and gathers by index. Production systems use grouped GEMMs (MegaBlocks) and expert parallelism.

moe.py
import torch
import torch.nn as nn
import torch.nn.functional as F


class SwiGLUExpert(nn.Module):
    def __init__(self, d_model: int, d_ff: int):
        super().__init__()
        self.w_gate = nn.Linear(d_model, d_ff, bias=False)
        self.w_up = nn.Linear(d_model, d_ff, bias=False)
        self.w_down = nn.Linear(d_ff, d_model, bias=False)

    def forward(self, x):
        return self.w_down(F.silu(self.w_gate(x)) * self.w_up(x))


class TopKMoE(nn.Module):
    def __init__(self, d_model, d_ff, n_experts=8, k=2, n_shared=0,
                 aux_coef=1e-2, z_coef=1e-3):
        super().__init__()
        self.n_experts, self.k = n_experts, k
        self.aux_coef, self.z_coef = aux_coef, z_coef
        self.router = nn.Linear(d_model, n_experts, bias=False)
        self.experts = nn.ModuleList(SwiGLUExpert(d_model, d_ff) for _ in range(n_experts))
        self.shared = nn.ModuleList(SwiGLUExpert(d_model, d_ff) for _ in range(n_shared))

    def forward(self, x):
        B, S, D = x.shape
        x_flat = x.reshape(-1, D)
        T = x_flat.shape[0]

        # Router math in fp32: bf16 logits lose precision in exp() and destabilize training.
        logits = self.router(x_flat).float()
        probs = logits.softmax(dim=-1)
        topk_p, topk_idx = probs.topk(self.k, dim=-1)
        # Renormalize over chosen experts (Mixtral convention) so outputs keep a stable scale.
        gates = (topk_p / topk_p.sum(dim=-1, keepdim=True)).to(x.dtype)

        out = torch.zeros_like(x_flat)
        for e in range(self.n_experts):
            token_ids, slot = (topk_idx == e).nonzero(as_tuple=True)
            if token_ids.numel() == 0:
                continue
            y = self.experts[e](x_flat[token_ids])
            out.index_add_(0, token_ids, y * gates[token_ids, slot, None])

        for s in self.shared:
            out = out + s(x_flat)

        # f is an argmax count and carries no gradient; P carries the gradient back to the router.
        counts = F.one_hot(topk_idx, self.n_experts).sum(dim=(0, 1)).float()
        f = counts / (T * self.k)
        P = probs.mean(dim=0)
        aux_loss = self.aux_coef * self.n_experts * (f * P).sum()
        z_loss = self.z_coef * torch.logsumexp(logits, dim=-1).pow(2).mean()

        self.last_load = f.detach()
        return out.reshape(B, S, D), aux_loss + z_loss
moe.py (self-check)
if __name__ == "__main__":
    torch.manual_seed(0)
    moe = TopKMoE(d_model=64, d_ff=128, n_experts=8, k=2, n_shared=1)
    x = torch.randn(4, 32, 64)
    y, aux = moe(x)
    assert y.shape == x.shape

    # Overfit a random regression target and watch the load stay spread across experts.
    target = torch.randn_like(x)
    opt = torch.optim.AdamW(moe.parameters(), lr=3e-3)
    for step in range(300):
        y, aux = moe(x)
        loss = F.mse_loss(y, target) + aux
        opt.zero_grad(); loss.backward(); opt.step()
        if step % 100 == 0:
            print(step, f"mse={F.mse_loss(y, target).item():.3f}",
                  "load=", [round(v, 3) for v in moe.last_load.tolist()])
    # Uniform load would be 1/8 = 0.125 per expert.
    assert moe.last_load.max() < 0.5, "router collapsed onto one expert"
  • Set aux_coef=0 and watch whether load drifts toward a few experts.
  • Compute topk-then-softmax over the selected logits and confirm the gates are identical.
  • Add a capacity limit: keep the first C tokens per expert and count drops as CF varies.

12Inference

Memory follows total parameters and FLOPs follow active

  • Prefill is compute-bound and gains fully from sparsity.
  • The sweet spot is large batches with enough tokens per expert, which is why MoE serving uses expert parallelism across many GPUs.
  • Offloading: most experts are idle for any token, so CPU offload and expert caching beat offloading dense layers, at a latency cost.
  • Fine-tuning: MoEs overfit and were unstable (ST-MoE). Lower the learning rate, keep or raise the aux loss, sometimes freeze the router.

+Wrap-up

Check the ideas, then build the project

Common confusions

  • Mixtral 8x7B has 56B parameters.

    Only FFNs are replicated; attention, norms and embeddings are shared. It has about 46.7B total and 12.9B active.

  • An MoE is an ensemble of models.

    Routing is per token and per layer. One sequence passes through many experts, and consecutive layers route independently.

  • Experts are topic specialists.

    Mostly not in coarse MoEs; specialization is often syntactic. Finer-grained experts show more domain specialization.

  • Active parameters determine memory.

    Active parameters set FLOPs per token. Total parameters set memory.

  • The aux loss makes routing uniform per token.

    It balances aggregate load over a batch. Individual tokens still route sharply.

  • Dropless means balancing does not matter.

    It removes the quality loss from dropping, but imbalance still makes one device the straggler.

  • Aux-loss-free means no balancing objective.

    The bias update is a balancing mechanism; it just sends no gradient into the model. DeepSeek-V3 even keeps a tiny sequence-level aux loss.

Check yourself

  1. A model has 32 experts per layer with top-4 routing, each expert shaped like the dense FFN of a 2B model. How do FLOPs per token and memory compare with the 2B dense model?

    Show answer

    Each token uses 4 experts, so FFN compute is about 4x the dense FFN (attention unchanged), somewhat under 4x overall. Memory holds 32 FFNs, so FFN parameters are 32x; total memory is roughly an order of magnitude larger, dominated by the experts.

  2. Why can you not directly minimize the variance of \(f_i\) by gradient descent, and how does the \(f_i P_i\) product get around it?

    Show answer

    \(f_i\) comes from TopK, which is piecewise constant, so its gradient is zero almost everywhere. Multiplying by the differentiable mean probability \(P_i\) gives gradient \(\alpha E f_i\) on \(P_i\), so overloaded experts lose the most probability. Where \(f \approx P\), the loss behaves like \(E \sum f_i^2\), minimized at uniform load.

  3. With \(T = 4096\), \(E = 64\), \(k = 8\) and CF 1.25, what is the capacity? What happens to the 600th token assigned to an expert?

    Show answer

    \(C = \lceil 1.25 \cdot 4096 \cdot 8 / 64 \rceil = 640\). The 600th token fits. A token beyond the 640th is dropped: it skips that expert and only its residual (plus any other selected experts) carries forward.

  4. What problem does the router z-loss solve that the load-balancing loss does not?

    Show answer

    Logit magnitude. The balancing loss cares which experts are chosen. The z-loss keeps logits small so softmax does not saturate and bf16 exponentiation keeps precision, which ST-MoE found to cause instability.

  5. In DeepSeek-V3 aux-loss-free balancing, why is the bias \(b_i\) added only for TopK selection and not to the gate \(g_i\)?

    Show answer

    The bias is a control signal for load, not a statement of how useful an expert is for this token. Adding it to the gate would change the output and the loss, bringing back the interference with language modeling that the method avoids.

  6. Why is MoE decoding relatively faster at batch size 1 than at batch size 256, compared with a dense model of the same active parameters?

    Show answer

    At batch 1 each token reads only its \(k\) experts per layer, so bytes read are about the active parameters. At batch 256 the union of selected experts covers nearly all experts, so each step reads close to the total parameters for the same active compute, and memory bandwidth is the bottleneck.

Chapter project

Turn your GPT-2 into an MoE and measure the trade

Swap the FFN in every other block for TopKMoE and compare against the dense model on the same data and steps.

  1. Take your Fundamentals GPT-2 (124M-style). Replace the FFN in every other block with TopKMoE (8 experts, top-2, each the size of the original FFN, or half-size for a fine-grained variant).
  2. Train dense and MoE on the same data (a few hundred million tokens of FineWeb-Edu or TinyStories) for the same steps. Log loss vs tokens and loss vs wall-clock.
  3. Report total params, active params, tokens/sec, peak memory and final validation loss.
  4. Ablate: (a) aux_coef = 0, (b) z_coef = 0, (c) top-1 vs top-2, (d) one shared expert. Plot per-expert load over training as an E × steps heatmap of last_load.
  5. Stretch: implement the DeepSeek-V3 bias update instead of the aux loss and compare balance and validation loss.
  6. Stretch: record each token's expert in layer L/2 and check whether code, numbers, punctuation or a language cluster on specific experts.
  • Table of params, tokens/sec, memory and validation loss for both models.
  • Four load heatmaps, one per ablation.
  • A one-page summary of the parameter, compute and quality trade.
