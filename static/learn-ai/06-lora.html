Chapter 6 · LLM Advanced

Freeze the model, learn a small low-rank correction

Full fine-tuning copies and re-optimizes every weight. LoRA keeps the base frozen and trains two thin matrices per layer: less memory, tiny checkpoints, many adapters on one base.

5 sections · needs: AdamW state, ZeRO/FSDP accounting, q/k/v/o and MLP projections, SFT and DPO

01Intuition

Full fine-tuning pays 16 bytes per weight, and a small update does not need to

Mixed-precision AdamW stores 16 bytes per parameter before activations. For an 8B model that is about 128 GB; for 70B, about 1.1 TB. ZeRO-3 and FSDP spread it over GPUs but do not shrink the total.

A LoRA checkpoint is tens to hundreds of MB, not another 16 GB copy, so serving ten customer variants no longer means ten models in GPU memory.

Pretraining already learned the features; fine-tuning mostly steers them. LoRA's bet (Hu et al., 2021) is that this move is low-rank in each weight matrix.

02The math

LoRA learns two thin matrices, A down and B up, instead of one full update

Initialization: why B = 0

The scaling factor

With Adam the update size is about the learning rate whatever the gradient, so dividing by r was meant to keep ΔW steady across ranks. In practice set α once (α = r, 2r, or a fixed 16 or 32) and treat it as part of the learning rate.

Which modules to target

The 2021 paper adapted only the query and value projections. That advice is outdated. QLoRA found all linear layers necessary to match full fine-tuning, and MLP-only LoRA beat attention-only at equal parameter count. Embeddings and the LM head stay frozen unless you add new tokens; then train them via modules_to_save.

03Code

A LoRA layer is about thirty lines, and PEFT wraps every layer for you

lora_linear.py
import math
import torch
import torch.nn as nn


class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r: int = 8, alpha: float = 16,
                 dropout: float = 0.0, rslora: bool = False):
        super().__init__()
        self.base = base
        self.base.weight.requires_grad_(False)   # the pretrained weight is never updated
        if self.base.bias is not None:
            self.base.bias.requires_grad_(False)
        d_out, d_in = base.weight.shape
        # rsLoRA divides by sqrt(r) so the update does not shrink as rank grows
        self.scaling = alpha / math.sqrt(r) if rslora else alpha / r
        self.A = nn.Parameter(torch.empty(r, d_in))
        self.B = nn.Parameter(torch.zeros(d_out, r))   # B = 0 makes the adapted model start identical to the base
        nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))  # A must be random or B's gradient would be zero forever
        self.dropout = nn.Dropout(dropout)
        self.merged = False

    def forward(self, x):
        out = self.base(x)
        if self.merged:
            return out
        # x @ A^T @ B^T keeps the intermediate at width r instead of materializing a d_out x d_in matrix
        return out + (self.dropout(x) @ self.A.T @ self.B.T) * self.scaling

    @torch.no_grad()
    def merge(self):
        if not self.merged:
            self.base.weight += (self.B @ self.A) * self.scaling
            self.merged = True

    @torch.no_grad()
    def unmerge(self):
        if self.merged:
            self.base.weight -= (self.B @ self.A) * self.scaling
            self.merged = False

The test below checks the three properties that matter: identical output at init, fitting a hidden low-rank change, and exact merge and unmerge.

check.py
torch.manual_seed(0)
d_in, d_out, r = 64, 32, 4
base = nn.Linear(d_in, d_out)
layer = LoRALinear(base, r=r, alpha=8)
x = torch.randn(256, d_in)

# B = 0 at init, so the wrapped layer is exactly the base layer
assert torch.allclose(layer(x), base(x))

trainable = sum(p.numel() for p in layer.parameters() if p.requires_grad)
total = sum(p.numel() for p in layer.parameters())
print(f"trainable {trainable} / {total} ({100 * trainable / total:.1f}%)")

# Target: the base layer plus a hidden rank-2 change; LoRA with r=4 should fit it
with torch.no_grad():
    delta = torch.randn(d_out, 2) @ torch.randn(2, d_in) * 0.1
    y = x @ (base.weight + delta).T + base.bias
opt = torch.optim.AdamW([p for p in layer.parameters() if p.requires_grad], lr=1e-2)
for step in range(2000):
    loss = ((layer(x) - y) ** 2).mean()
    opt.zero_grad()
    loss.backward()
    opt.step()
assert loss.item() < 1e-4

before = layer(x)
layer.merge()
assert torch.allclose(layer(x), before, atol=1e-5)  # merging must not change outputs
layer.unmerge()
assert torch.allclose(layer(x), before, atol=1e-5)

Change the hidden delta to rank 8 while keeping r=4: the loss plateaus well above zero. That is the capacity limit from section 05. peft_qlora.py
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

model_id = "meta-llama/Llama-3.2-1B"  # any causal LM works; this one is small enough for a single consumer GPU

# QLoRA: frozen base stored in 4-bit NF4, matmuls computed in bf16
bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(model_id, quantization_config=bnb, device_map="auto")
# Casts norms to fp32 and enables gradient checkpointing, which 4-bit training needs for stability and memory
model = prepare_model_for_kbit_training(model)

config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules="all-linear",   # attention and MLP projections; MLPs matter most
    task_type="CAUSAL_LM",
    # use_rslora=True,             # switch on when going to high ranks
    # use_dora=True,               # magnitude/direction decomposition, slower per step
)
model = get_peft_model(model, config)
model.print_trainable_parameters()

# ... train with transformers.Trainer or TRL's SFTTrainer / DPOTrainer as in the fundamentals course ...

model.save_pretrained("my-adapter")   # writes only the adapter, tens of MB

# Merging: reload the base in bf16, not 4-bit, so the merged weights are not requantized
from peft import PeftModel
base = AutoModelForCausalLM.from_pretrained(model_id, torch_dtype=torch.bfloat16)
merged = PeftModel.from_pretrained(base, "my-adapter").merge_and_unload()
merged.save_pretrained("my-merged-model")

TRL's SFTTrainer and DPOTrainer accept a peft_config directly. For LoRA+, PEFT provides peft.optimizers.create_loraplus_optimizer.

04Variants

Each variant fixes one edge of plain LoRA

QLoRA: store the frozen base in 4 bits

If the base never changes, why keep it in 16 bits? QLoRA (Dettmers et al., 2023) quantizes it to 4 bits and trains bf16 adapters on top, backpropagating through the dequantized weights. It fine-tuned a 65B model on one 48 GB GPU with no measurable loss versus 16-bit LoRA on their benchmarks.

NF4. Pretrained weights are roughly zero-mean normal, so a uniform 4-bit grid wastes levels in the tails. NF4 puts its 16 levels at quantiles of a normal distribution, with an exact zero, so each level is used about equally often.

Double quantization. One fp32 constant per 64 weights costs 0.5 bits per parameter. QLoRA quantizes the constants to 8 bits in blocks of 256, with one fp32 constant per block of constants.

Paged optimizers. Long sequences spike memory during gradient checkpointing and can OOM a job that otherwise fits. QLoRA keeps optimizer states in NVIDIA unified memory, so they page to CPU RAM under pressure, like virtual memory.

Tradeoffs: QLoRA is slower per step than bf16 LoRA because every forward and backward dequantizes, and the adapter is trained against a quantized base. Deploy it on that base, or merge carefully (Fig. 9).

DoRA: split magnitude from direction

DoRA (Liu et al., 2024) found that full fine-tuning changes a weight's magnitude and direction in opposite proportions, while LoRA changes both together. It reparameterizes so that BA moves only direction and a trained vector m moves only magnitude. It usually beats LoRA at the same rank, especially at low rank, and merges to a plain matrix. The price is a norm recomputed every step.

LoRA+: give B a bigger learning rate

A and B play asymmetric roles, so one shared learning rate makes feature learning inefficient in the large-width limit (Hayou et al., 2024). The fix is one line: \(\eta_B = \lambda\,\eta_A\) with \(\lambda\) around 16. They report up to about 2x faster convergence and small accuracy gains, at no extra cost.

Serving many adapters

Adapters are small and the base is shared, so one GPU can serve many fine-tuned models. Keep W0 shared and give each request its own adapter; the big matmul is shared across the batch and the small ones use gather-style kernels (Punica's SGMV is the well-known one).

S-LoRA (Sheng et al., 2023) scales this to thousands of adapters: adapters live in CPU memory and page into GPU memory on demand, a unified pool manages adapter weights of varying rank together with the KV cache to avoid fragmentation, custom kernels batch heterogeneous ranks, and tensor parallelism is extended to adapters. It reported up to 4x throughput over vLLM with naive adapter support. vLLM and SGLang support multi-LoRA out of the box; in vLLM use enable_lora=True and pass a LoRARequest per request.

05Modern practice

LoRA matches full fine-tuning until the data outgrows the adapter

LoRA learns less and forgets less

Biderman et al. (2024) compared LoRA and full fine-tuning on Llama-2 7B for continued pretraining and instruction tuning, in code and math.

  • Learns less. LoRA substantially underperformed on the target domain, most of all for continued pretraining on code; the gap was smaller for instruction tuning.
  • Forgets less. It preserved out-of-domain skills better, acting as a regularizer stronger than weight decay or dropout.
  • Full updates are not low-rank. The spectrum of ΔW from full fine-tuning has rank 10 to 100 times higher than typical LoRA configurations.

LoRA Without Regret

Thinking Machines (2025) refined this with careful sweeps. Apply LoRA to all layers, especially MLPs. LoRA is also less tolerant of large batch sizes than full fine-tuning.

LoRA is an excellent default for instruction tuning, preference optimization, RL and style or format adaptation. To inject large volumes of new knowledge (a new language, a large codebase, continued pretraining), prefer full fine-tuning, or at least much larger ranks with rsLoRA, and measure.

Practical hyperparameters

Sebastian Raschka's experiments add three points: QLoRA saves about a third of memory versus LoRA at a moderate cost in runtime, \(\alpha = 2r\) is a reasonable heuristic, and results are consistent across random seeds, so one careful run is informative.

06Wrap-up

Check the ideas before the project

Common confusions

  • LoRA makes inference faster.

    A merged LoRA model is exactly as fast as the base; unmerged adapters add a small cost. LoRA saves training memory, storage and multi-tenant serving memory.

  • LoRA reduces activation memory.

    Barely. Activations depend on the base width and sequence length, and backprop still flows through every frozen layer. Use gradient checkpointing.

  • Higher rank is always better.

    With standard α/r scaling, very high ranks can train worse because the update is scaled down. Use rsLoRA, and remember module coverage usually matters more than rank.

  • Initializing B = 0 means nothing trains.

    B's gradient depends on the random A, so B moves on step one and then A gets gradients too. Only initializing both to zero is broken.

  • QLoRA trains a 4-bit model.

    The base is stored in 4-bit and frozen; adapters and all computation are bf16. The trainable parameters are never quantized.

  • Merging a QLoRA adapter is free.

    Merging into 4-bit weights requires requantization and changes outputs. Merge into a bf16 copy of the base.

  • LoRA is just a cheaper approximation of full fine-tuning.

    It is also a different inductive bias: it forgets less, which is sometimes exactly what you want.

Check yourself

  1. For a \(4096 \times 14336\) MLP projection, how many trainable parameters does LoRA add at \(r = 16\), and what fraction of the full matrix is that?

    Show answer

    The adapter has \(r(d_{\text{in}} + d_{\text{out}})\) parameters: \(16 \times 18{,}432 = 294{,}912\). The full matrix has \(58{,}720{,}256\) entries, so about 0.5%.

  2. Why does LoRA initialize B to zero and A randomly, rather than both random or both zero?

    Show answer

    B = 0 makes ΔW = 0 at the start, so training begins exactly at the pretrained model. A must be random so that B's gradient, proportional to \(Ax\), is nonzero; if both were zero all gradients would vanish. If both were random, the model would start at a randomly perturbed, worse point.

  3. You raise \(r\) from 16 to 256 with standard scaling and keep \(\alpha = 16\). Training gets worse. Explain why, and give two fixes.

    Show answer

    The update is scaled by \(\alpha/r = 16/256 = 0.0625\) instead of 1, so its effective step shrinks and, per rsLoRA's analysis, learning at high rank slows or collapses. Fixes: use rsLoRA scaling \(\alpha/\sqrt{r}\); raise \(\alpha\) proportionally (for example \(\alpha = 2r\)); or re-tune the learning rate upward.

  4. In QLoRA, what does NF4 optimize for, and what problem does double quantization solve? Do the overhead arithmetic with and without it.

    Show answer

    NF4 places its 16 levels at quantiles of a normal distribution, so for normally distributed weights each level is used equally often, minimizing information loss. Double quantization cuts the overhead of per-block scale constants. Without it: one fp32 constant per 64 weights is \(32/64 = 0.5\) bits per parameter. With it: 8-bit constants plus one fp32 constant per 256 constants gives \(8/64 + 32/16384 \approx 0.127\) bits per parameter, saving about 0.37 bits per parameter.

  5. A team wants to serve 500 customer-specific fine-tunes of an 8B model. Compare memory for merged full checkpoints against a shared base with unmerged rank-16 adapters on all linear layers.

    Show answer

    Merged: \(500 \times 16\) GB \(= 8\) TB of bf16 weights, impossible to keep resident. Shared base: 16 GB once. A Llama-3-8B-style model has 32 layers with seven linear projections; at \(r = 16\) the adapter is roughly 40M to 45M parameters, about 85 MB in bf16. 500 of them is about 42 GB, and with S-LoRA-style paging only active adapters need to be on GPU.

  6. Your LoRA fine-tune on 20B tokens of a new programming language underperforms full fine-tuning, but your LoRA chat fine-tune on 50k examples matches it. Explain using the two studies in section 05.

    Show answer

    Biderman et al. found LoRA learns less in high-information regimes like continued pretraining, because full fine-tuning's updates there are high-rank. Thinking Machines found that when the dataset's information fits within the adapter's capacity, as with typical instruction tuning, a well-tuned LoRA matches full fine-tuning. 20B tokens of a new language exceeds that capacity; 50k chat examples does not.

Chapter project

Find LoRA's capacity limit on a real model

Compare full fine-tuning, your own LoRA and PEFT on a small instruct model (Llama-3.2-1B-Instruct or Qwen2.5-0.5B-Instruct), on a low-information task and a high-information one.

  1. Pick two datasets: (a) a small style or format task, such as 2k examples answering in a strict JSON schema; (b) a knowledge-heavy task, such as 50M+ tokens of a domain corpus (a language's documentation, legal texts, or a non-English Wikipedia subset).
  2. Fine-tune with full fine-tuning; your LoRALinear on all linear layers at \(r \in \{4, 32, 256\}\); and PEFT LoRA at \(r = 256\) with use_rslora=True. Sweep the learning rate for each (at least three values) and keep the best.
  3. Measure target-domain loss or accuracy, and forgetting on a held-out general benchmark (a few hundred MMLU or HellaSwag questions).
  4. Plot target performance against forgetting for every run. Say where LoRA matches full fine-tuning and where it falls short.
  5. Bonus: repeat the best LoRA configuration with QLoRA and DoRA and report memory, step time and quality. Then serve two adapters from one base with vLLM's multi-LoRA support and confirm each request gets its own behavior.
