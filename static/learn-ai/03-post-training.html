Chapter 3 · LLM Fundamentals

Post-training teaches a base model how to behave

A pretrained model knows the facts but not the role. Three stages (SFT, preferences, verifiable RL) give it an assistant’s behavior for a small fraction of pretraining compute.

5 sections + project · needs: causal LM loss, a transformer training loop, KL divergence, the sigmoid

01Overview

A base model continues text; post-training makes it answer

Pretraining optimized the model to continue documents. On the web a question is often followed by more questions, so a base model answers with a quiz. Post-training shifts which part of that distribution the model samples from. It adds little new knowledge.

Three stages, three signals

  • SFT learns format and role from (prompt, ideal response) pairs. It is imitation.
  • Preference tuning learns taste from pairs where one answer is better. RLHF with PPO, or DPO.
  • RLVR learns from programmatic checks: math answers, code tests, format constraints.

The goals are helpful, honest, harmless, with instruction following as the prerequisite. They conflict: maximal helpfulness says answer everything, maximal harmlessness says refuse when unsure. Post-training also targets latent capabilities: reasoning, tool use, long agent tasks, and following a system prompt.

Serving with a template that differs from training (a missing system header, a wrong newline, no BOS token) silently degrades quality. In Hugging Face the template is a Jinja program stored with the tokenizer.

chat_template.py
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM2-135M-Instruct")
messages = [
    {"role": "system", "content": "You are terse."},
    {"role": "user", "content": "Capital of France?"},
]
# add_generation_prompt appends the assistant header so the model's next token
# is the start of the answer, not a guess at who speaks next.
text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
print(text)
ids = tok.apply_chat_template(messages, add_generation_prompt=True)
print([tok.decode([i]) for i in ids][:12])

Run it and look at how the special tokens appear as single tokens in the decoded list.

Common confusions

  • Post-training adds knowledge.

    Mostly no. It changes behavior and elicits latent skill. New facts belong in continued pretraining or retrieval; SFT on new facts tends to increase hallucination.

  • RLHF means the whole pipeline.

    People use it loosely. Strictly it is the reward-model-plus-RL stage.

  • The chat template is cosmetic.

    It is part of the input distribution. A mismatch between training and serving silently hurts quality.

  • Special tokens are just strings.

    They are distinct vocabulary ids. With special-token parsing off, the literal text <|eot_id|> becomes several ordinary tokens.

  • Instruct and chat are different things.

    Today the terms are interchangeable. Historically instruct meant single-turn and chat meant multi-turn.

Check yourself

  1. A base model answers your question with more questions. Why, in terms of the pretraining objective?

    Show answer

    Pretraining maximizes likelihood of web text, where a question is often followed by other questions. The model continues the document in the most likely way, which need not be an answer.

  2. What are the three stages of the modern pipeline, and what signal does each use?

    Show answer

    SFT uses demonstrations. Preference tuning uses comparisons. RLVR uses programmatic correctness checks on sampled outputs.

  3. Why must role markers be special tokens rather than plain text?

    Show answer

    So users cannot forge structure. User text tokenizes to ordinary tokens, so the model can tell a real system turn from a user pretending to write one.

  4. What goes wrong if SFT data never trains the end-of-turn token?

    Show answer

    The model never learns to stop. It keeps generating past its answer, often inventing a new user turn.

  5. What was the most striking result of InstructGPT?

    Show answer

    Labelers preferred the 1.3B InstructGPT outputs over the 175B GPT-3 base model: post-training can matter more than a 100x parameter increase for user-facing quality.

02Supervised fine-tuning

SFT is next-token loss on the assistant's tokens only

SFT is the pretraining loop pointed at conversations, with one twist: loss only on assistant tokens. You teach the model to respond to prompts, not to write them. It sets the default persona and format, and it is cheap, stable and predictable.

Why mask the prompt? The gradient budget goes to responses, long prompts dilute the signal, and you do not want the model to learn to write jailbreaks. Masking is the standard default. In PyTorch, label -100 is skipped by F.cross_entropy.

sft_masking.py
import torch
import torch.nn.functional as F

IGNORE = -100

def build_labels(segments):
    """segments: list of (token_ids, trainable). Returns input_ids, labels."""
    input_ids, labels = [], []
    for ids, trainable in segments:
        input_ids += ids
        labels += ids if trainable else [IGNORE] * len(ids)
    return torch.tensor(input_ids), torch.tensor(labels)

def sft_loss(logits, labels):
    # Position t predicts token t+1, so drop the last logit and the first label.
    logits = logits[:, :-1, :]
    labels = labels[:, 1:]
    return F.cross_entropy(
        logits.reshape(-1, logits.size(-1)),
        labels.reshape(-1),
        ignore_index=IGNORE,  # averages only over assistant tokens
    )

prompt = [1, 50, 51, 52, 2]      # header + prompt
answer = [60, 3]                  # answer + end-of-turn
input_ids, labels = build_labels([(prompt, False), (answer, True)])
input_ids, labels = input_ids[None], labels[None]

vocab = 100
logits = torch.randn(1, input_ids.size(1), vocab, requires_grad=True)
loss = sft_loss(logits, labels)
loss.backward()

# Only the logits at positions that predict answer tokens receive gradient.
grad_rows = logits.grad[0].abs().sum(-1) > 0
assert grad_rows.tolist() == [False, False, False, False, True, True, False]

Per-token averaging over a batch weights long responses more; per-example averaging weights every conversation equally. Gradient accumulation can silently mix the two. Recent Hugging Face trainers normalize by the total number of trained tokens.

Alpaca ran this recipe with text-davinci-003 and tuned LLaMA 7B on 52k pairs. The general pattern is distillation: a strong teacher writes responses, a smaller student learns from them. Zephyr did this with UltraChat, and Tulu 3 generated persona-conditioned prompts with GPT-4o.

  • Terms of use. Many API terms forbid training competing models on outputs.
  • Inherited flaws. The student copies the teacher's style, errors and refusals.
  • Style over substance. "The False Promise of Imitating Proprietary LLMs" found students copied ChatGPT's confident tone far better than its accuracy.
  • Deduplicate, and decontaminate against your eval sets.
  • Filter for correctness where you can check it.
  • Balance the mix across task types.
  • Prefer diverse prompts over many responses to one prompt.
  • Read samples by hand.

Catastrophic forgetting: tuning on a narrow set can erase base skills. Keep the mix broad, use a low learning rate and few epochs, mix in pretraining-style data, or use LoRA, which forgets less but also learns less.

sft_trl.py
# pip install trl datasets
from datasets import load_dataset
from trl import SFTConfig, SFTTrainer

dataset = load_dataset("trl-lib/Capybara", split="train")  # conversational "messages" format

config = SFTConfig(
    output_dir="qwen3-0.6b-sft",
    learning_rate=2e-5,
    num_train_epochs=1,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,
    max_length=2048,
    packing=True,               # fills each sequence with several examples
    assistant_only_loss=True,   # the loss masking from the scratch version
)

trainer = SFTTrainer(model="Qwen/Qwen3-0.6B", args=config, train_dataset=dataset)
trainer.train()

assistant_only_loss relies on the chat template marking assistant spans with {% generation %} tags. TRL patches common families; for an unusual model, check it, or your "masked" run trains on everything. Prompt-completion datasets mask the prompt by default.

Common confusions

  • Loss masking means the model does not see the prompt.

    It sees the prompt fully. Only the loss terms for predicting prompt tokens are dropped.

  • Lower SFT loss means a better chat model.

    Training loss falls with memorization. Judge by generation evals.

  • LIMA says 1,000 examples is enough.

    It says style alignment is cheap given a strong base. Math or tool calling still benefit from much more targeted data.

  • Packing is always free.

    Only with per-example attention masks and position resets. Otherwise examples contaminate each other.

  • Synthetic data is lower quality than human data.

    Often the opposite today. The risks differ: inherited bias, licensing, and model collapse when you iterate on unfiltered self-output.

Check yourself

  1. Write the masked SFT loss. What does \(m_t\) do, and why is the final prompt position still trained?

    Show answer

    \(\mathcal{L} = -\frac{1}{\sum_t m_t}\sum_t m_t \log p_\theta(x_t \mid x_{<t})\). \(m_t\) selects which targets contribute. The last prompt position (the assistant header) predicts the first assistant token, a target with \(m_t = 1\) after the shift.

  2. Why prefer distilled synthetic data over human demonstrations, and what are two risks?

    Show answer

    It is cheaper, faster, more consistent, and covers many skills. Risks: the student copies the teacher's style and errors, API terms may forbid it, and iterating on unfiltered self-generated data collapses diversity.

  3. What problem does packing solve, and what extra machinery does correct packing need?

    Show answer

    It avoids padding waste when lengths vary. Correct packing needs attention masks that stop cross-example attention and position ids reset per example, or a varlen kernel.

  4. State the Superficial Alignment Hypothesis. What does it not imply?

    Show answer

    Knowledge comes from pretraining; alignment mostly teaches format and style. It does not imply targeted SFT data is useless for specific skills, nor that preference tuning has no value.

  5. Training loss falls steadily but MT-Bench style scores dropped after epoch 2. What is happening, and what would you change?

    Show answer

    Overfitting. Stop earlier (1 to 2 epochs), lower the learning rate, add diversity, and select checkpoints by downstream evals.

03Preference optimization

Preferences teach taste, and DPO folds the reward model into the policy

SFT imitates one answer per prompt. But many answers are acceptable, and judging which of two is better is easier and more consistent than writing a perfect one. Preference data uses that asymmetry, and lets the model learn from its own mistakes.

A reward model is usually the SFT model with a linear head that outputs one scalar at the last response token. It reaches 65% to 80% accuracy on held-out pairs, roughly the ceiling set by label noise. It is a learned proxy, wrong in exploitable ways.

Practical notes. \(\log \pi(y\mid x)\) is the sum of response token log-probs, with the same masking as SFT. The learning rate is tiny, around \(5\times 10^{-7}\) for 7B to 8B models, 10x to 50x below SFT. Training needs only forward passes on fixed pairs: no sampling, no value model, no RL.

Every variant takes the same inputs: summed log-probs of chosen and rejected under the policy and the reference, plus response lengths.

preference_losses.py
import torch
import torch.nn.functional as F

def sequence_logprob(logits, labels, ignore_index=-100):
    """Sum of log p(token) over response tokens. Same shift and mask as SFT."""
    logits, labels = logits[:, :-1], labels[:, 1:]
    mask = labels != ignore_index
    safe = labels.masked_fill(~mask, 0)  # gather needs a valid index everywhere
    logps = torch.log_softmax(logits, -1).gather(-1, safe[..., None]).squeeze(-1)
    return (logps * mask).sum(-1), mask.sum(-1)

def preference_loss(pi_w, pi_l, ref_w, ref_l, len_w, len_l,
                    kind="dpo", beta=0.1, gamma=0.5):
    if kind == "dpo":
        logits = beta * ((pi_w - ref_w) - (pi_l - ref_l))
        return -F.logsigmoid(logits).mean()
    if kind == "dpo_norm":  # Tulu 3 length-normalized DPO; beta is much larger (e.g. 5)
        logits = beta * ((pi_w - ref_w) / len_w - (pi_l - ref_l) / len_l)
        return -F.logsigmoid(logits).mean()
    if kind == "ipo":  # beta plays the role of tau; regress the margin to a target
        h = (pi_w - ref_w) - (pi_l - ref_l)
        return ((h - 1 / (2 * beta)) ** 2).mean()
    if kind == "simpo":  # no reference model, average log-prob, margin gamma
        logits = beta * (pi_w / len_w - pi_l / len_l) - gamma
        return -F.logsigmoid(logits).mean()
    raise ValueError(kind)

# Sanity checks on a toy batch of 2 pairs.
pi_w, pi_l = torch.tensor([-10.0, -20.0]), torch.tensor([-12.0, -18.0])
ref_w, ref_l = torch.tensor([-11.0, -19.0]), torch.tensor([-11.0, -19.0])
len_w, len_l = torch.tensor([5.0, 10.0]), torch.tensor([6.0, 9.0])

# At pi == ref the DPO logit is 0, so the loss is log 2 whatever the data.
assert torch.isclose(preference_loss(ref_w, ref_l, ref_w, ref_l, len_w, len_l),
                     torch.log(torch.tensor(2.0)))

# Pushing the chosen log-prob up must lower the DPO loss.
better = preference_loss(pi_w + 1, pi_l, ref_w, ref_l, len_w, len_l)
assert better < preference_loss(pi_w, pi_l, ref_w, ref_l, len_w, len_l)

# sequence_logprob on a toy model output: 1 sequence, 4 positions, vocab 3.
logits = torch.zeros(1, 4, 3)            # uniform predictions
labels = torch.tensor([[-100, -100, 1, 2]])  # last two tokens are the response
lp, n = sequence_logprob(logits, labels)
assert n.item() == 2 and torch.isclose(lp, 2 * torch.log(torch.tensor(1 / 3))).all()

In a real run, compute pi_w and pi_l with one policy forward pass over the concatenated batch. Compute ref_w and ref_l under torch.no_grad(), or precompute them once. TRL's DPOTrainer does this; loss_type picks the variant ("sigmoid" is DPO).

Variants fix specific weaknesses

Online or offline

Goodhart's law applies to reward models

The most pervasive hack is length: judges prefer longer answers, so reward models learn that length pays. Singhal et al. found that much of the measured RLHF gain in some setups could be reproduced by optimizing length alone. DPO is not immune, because summed log-probs make the implicit reward length-dependent. Mitigations:

  • Length-normalized objectives (SimPO, LN-DPO) or explicit length penalties.
  • Length-controlled evaluation (AlpacaEval 2 length-controlled win rate).
  • Balanced chosen and rejected lengths.
  • Stronger KL, early stopping, RM ensembles.
  • Verifiable rewards where possible: they cannot be flattered.
Common confusions

  • DPO has no reward model.

    It has one implicitly: \(\beta \log \pi_\theta/\pi_{\text{ref}}\). It just never trains a separate network.

  • DPO is equivalent to RLHF.

    Same optimum in theory, with infinite data and a perfect fit. In practice offline DPO and online PPO see different data.

  • Higher \(\beta\) means stronger preference learning.

    The opposite. Higher \(\beta\) pulls harder toward the reference model.

  • The chosen log-prob should go up during DPO.

    Often it goes down. Only the margin is guaranteed to grow.

  • Reward model accuracy is what matters.

    A more accurate RM can still give a worse policy if it is easier to exploit. Evaluate the policy.

Check yourself

  1. Under Bradley-Terry, what is the preference probability when rewards differ by 0? By 2? Why does adding a constant to all rewards change nothing?

    Show answer

    \(\sigma(0) = 0.5\); \(\sigma(2) \approx 0.88\). Only the difference \(r(y_w) - r(y_l)\) enters, so a shared constant cancels.

  2. Why does the RLHF objective include a KL penalty to a reference policy?

    Show answer

    The reward model is reliable only near its training distribution. The penalty limits reward hacking and preserves fluency and knowledge.

  3. In the DPO derivation, where does \(Z(x)\) go, and why is that the crucial step?

    Show answer

    It cancels when the implicit rewards of two responses to the same prompt are subtracted inside Bradley-Terry. \(Z(x)\) sums over all responses and is intractable, so without the cancellation the loss could not be computed.

  4. Name one problem each that IPO, KTO, ORPO and SimPO address.

    Show answer

    IPO: with deterministic preferences DPO ignores its KL regularization; IPO regresses to a finite margin. KTO: needs only unpaired thumbs-up or down. ORPO: drops the reference model and the separate SFT stage. SimPO: drops the reference model and uses length-normalized rewards against length bias.

  5. Give two reasons offline DPO can underperform online RLHF, and one way to narrow the gap without PPO.

    Show answer

    Offline pairs are off-policy, so the model ranks responses it would not generate, and it cannot find and fix its current mistakes. Narrow the gap with on-policy pair generation or iterative DPO rounds.

04Tools and safety tuning

The model writes a request; the runtime does the work

A language model cannot call an API. It emits text in a format the runtime recognizes, then reads the result when the runtime appends it to the context. "Function calling" is a protocol layered on the chat template.

trajectory.txt
<|im_start|>system
You can call tools. Tools: [{"name": "get_weather", "parameters": {"city": "string"}}]<|im_end|>
<|im_start|>user
Should I bring an umbrella in Oslo?<|im_end|>
<|im_start|>assistant
<tool_call>{"name": "get_weather", "arguments": {"city": "Oslo"}}</tool_call><|im_end|>
<|im_start|>tool
{"forecast": "rain", "precip_mm": 7}<|im_end|>
<|im_start|>assistant
Yes. Rain is forecast in Oslo with about 7 mm expected.<|im_end|>

Hugging Face's apply_chat_template accepts tools=[...] and renders schemas in each model's native format, the safest way to match training.

Tool use is learned like everything else: SFT on trajectories, then preference tuning or RL. Toolformer keeps only self-proposed API calls whose results lower the loss on the following tokens. Synthetic trajectories from a strong teacher, kept when they reach a verified answer, are now standard. Edge cases matter as much: no tool needed, a missing argument (ask), a tool error, parallel calls.

tool_spans.py
# Each message becomes a span; only assistant spans carry loss.
TRAINABLE_ROLES = {"assistant"}

def spans_for(messages):
    spans = []
    for m in messages:
        body = m["content"] if "tool_call" not in m else f'<tool_call>{m["tool_call"]}</tool_call>'
        spans.append((f'<|{m["role"]}|>{body}<|end|>', m["role"] in TRAINABLE_ROLES))
    return spans

traj = [
    {"role": "user", "content": "Weather in Oslo?"},
    {"role": "assistant", "tool_call": '{"name": "get_weather", "arguments": {"city": "Oslo"}}'},
    {"role": "tool", "content": '{"forecast": "rain"}'},
    {"role": "assistant", "content": "Rain is forecast in Oslo."},
]
spans = spans_for(traj)
for text, trainable in spans:
    print("TRAIN" if trainable else "mask ", text)

# Tool output is evidence to condition on, never a target the model should generate.
assert [t for _, t in spans] == [False, True, False, True]

Real implementations do this at the token level, as in section 02: role headers masked, only the assistant body plus its end-of-turn token trained.

Modern agents keep this loop, but the thought may be a hidden reasoning block and actions use native tool-call tokens. Agentic post-training targets tasks of dozens or hundreds of steps and tens of thousands of tokens. The signal is outcome-level (did the tests pass), which pushes toward RLVR in sandboxes. The environment itself becomes part of the dataset: containers, tool simulators and graders are often more engineering than the training loop.

Safety tuning has two failure modes

Red teaming (humans and attacker LLMs) searches for prompts that elicit harm. Successful attacks become training data and regression tests. Jailbreaks use role-play framing, obfuscation, many-shot priming with fabricated dialog, or optimized suffixes. They work because safety training covers a finite region of input space while the capability stays in the weights. Defense is layered: adversarial training, input and output classifiers, system controls.

Constitutional AI (Bai et al., 2022) reported models that were both more harmless and less evasive than ones trained on human harmlessness labels. Humans still write the principles and evaluate the results. Rule-based rewards (Mu et al., 2024) grade fine-grained propositions ("contains an apology", "refuses", "is judgmental") with an LLM. Changing policy means editing rules, and the rules target over-refusal and preachiness directly.

This only works if the template makes provenance unambiguous, which is another reason role markers are special tokens (Wallace et al., 2024).

Common confusions

  • The model executes the tool.

    The model emits a structured request. The runtime executes it. Security lives in the runtime: sandboxes and permissions.

  • Train on tool outputs too, it is more data.

    That teaches the model to fabricate them. Mask them.

  • More refusals means a safer model.

    Past a point it means a less useful model with little added safety. Measure both failure modes.

  • Constitutional AI removes humans.

    Humans write the principles and evaluate. AI replaces most per-example labeling.

  • A strong system prompt stops prompt injection.

    Without instruction-hierarchy training and runtime controls, models follow instruction-like text wherever it appears.

Check yourself

  1. Walk through the four steps of a function call, and say which the model performs.

    Show answer

    Schemas go in the prompt; the model emits a structured call and stops; the runtime executes and appends the result as a tool message; the model continues. The model performs only the generation steps: the call and the later answer.

  2. In a tool-use SFT trajectory, which spans carry loss, and why not the tool output?

    Show answer

    Assistant spans: reasoning, tool calls, final answers, end-of-turn tokens. Tool output is masked so the model uses it as evidence and does not learn to generate (fabricate) results.

  3. What distinguishes ReAct from plain chain-of-thought?

    Show answer

    ReAct interleaves reasoning with actions and feeds observations back, so reasoning is grounded and corrected by real information. Chain-of-thought reasons only over what is already in context.

  4. Describe the two phases of Constitutional AI. What does each replace in classic RLHF?

    Show answer

    Supervised: self-critique and revision against principles, then SFT on revisions (replaces human harmless demonstrations). RL: AI-labeled preferences train a preference model for RL (replaces human harmlessness comparisons).

  5. What is prompt injection, and how does the instruction hierarchy address it?

    Show answer

    Instructions hidden in lower-trust content, such as tool outputs, that try to override the developer or user. The hierarchy trains the model to prioritize system over user over tool content and follow lower-level instructions only when they do not conflict.

05Case study on Tulu 3

Tulu 3 shows every stage, with the data and code published

Most frontier recipes are secret. AI2's Tulu 3 post-trains Llama 3.1 base models and releases the data, training code, evaluation code, decontamination tooling, checkpoints and a paper with ablations. At release the 8B and 70B models matched or beat Llama 3.1 Instruct on its evaluation suite.

The prompt pool mixes public sets (FLAN v2, WildChat, OpenAssistant, NuminaMath, Evol-CodeAlpaca, Aya, CoCoNot, WildGuardMix, WildJailbreak) with persona-driven synthetic data. GPT-4o writes a problem that a persona from Persona Hub (about 250k descriptions) would pose. Personas buy diversity, the main failure of naive synthetic generation.

Several popular public datasets turned out to contain benchmark test data. Without this step, reported scores partly measure memorization. The SFT mix itself was built skill by skill: train, check the target eval, merge, and ablate each dataset. Removing a skill's data removes the skill, and loss aggregation (per token or per example) measurably changed results.

RLVR uses PPO from the DPO checkpoint with a KL penalty to the reference and a value model initialized from a general reward model. A verifier cannot be flattered: no length bias, no sycophancy. It only applies where checking is cheap and reliable. With too little KL the policy overoptimized, gaming verifiers in ways that hurt other skills. At 70B, GSM8K was already saturated, so gains were smaller.

Verifiers are simple, and that is the point

verifiers.py
import re

def last_number(text):
    nums = re.findall(r"-?\d+(?:\.\d+)?", text.replace(",", ""))
    return float(nums[-1]) if nums else None

def math_reward(response, gold, alpha=10.0):
    # Only the final answer counts; the reasoning before it is free-form.
    pred = last_number(response)
    return alpha if pred is not None and abs(pred - float(gold)) < 1e-6 else 0.0

def word_count_reward(response, max_words, alpha=10.0):
    # IFEval-style constraint: deterministic, so the policy cannot argue its way to reward.
    return alpha if len(response.split()) <= max_words else 0.0

def lowercase_reward(response, alpha=10.0):
    return alpha if response == response.lower() else 0.0

assert math_reward("3 apples + 4 apples, so the answer is 7.", "7") == 10.0
assert math_reward("The answer is 1,250", "1250") == 10.0
assert math_reward("I think it is 8", "7") == 0.0
assert word_count_reward("short answer here", 5) == 10.0
assert lowercase_reward("Hello") == 0.0
print("verifiers ok")

Llama 3 chose DPO over PPO for stability at 405B, masked formatting tokens out of the DPO loss, and added an NLL term on the chosen response. Its data is not released. Tulu 3 released everything, so you can reproduce a Llama 3.1 Instruct class run and ablate any decision.

Common confusions

  • RLVR replaces preference tuning.

    It complements it. Verifiable tasks are a subset; chat quality and safety still come from SFT and preferences.

  • Decontamination is only about exact matches.

    Paraphrased and partial overlaps also inflate scores. N-gram overlap is a practical approximation that still misses paraphrases.

  • On-policy DPO is online RL.

    Tulu 3's pairs were generated once from the SFT model. They are on-policy at the start, then increasingly off-policy. Iterating rounds moves closer to online.

  • Open weights means open recipe.

    Llama 3 is open-weight with a described recipe. Tulu 3 is open-weight, open-data, open-code. Only the latter is reproducible.

Check yourself

  1. Why did Tulu 3 split its evals into development and unseen sets?

    Show answer

    Repeatedly deciding on the same benchmarks overfits the recipe to them. The unseen set, touched only at the end, measures whether improvements generalize.

  2. Describe the decontamination rule. What contamination does it miss?

    Show answer

    8-gram matching on user turns: an instance is contaminated if more than 50% of its tokens are covered by matches with one training instance; datasets overlapping more than 2% of an eval were cleaned or dropped. It misses paraphrased or translated contamination and overlap below the n-gram length.

  3. Why is \(\beta\) in length-normalized DPO so much larger than in standard DPO?

    Show answer

    Dividing by token count turns summed log-ratios into small per-token averages. A larger \(\beta\) restores a useful scale for the sigmoid's input.

  4. What makes a reward verifiable, and what are the limits of RLVR?

    Show answer

    Correctness can be checked programmatically and reliably. Limits: only checkable tasks, verifier bugs can be gamed, and with weak KL it overoptimizes target skills at the expense of others.

  5. Name three differences between Llama 3 and Tulu 3 post-training.

    Show answer

    Any three: six iterative rounds vs one pass; large-scale human preferences vs LLM-judged; rejection sampling with an RM for SFT data; no RLVR or PPO vs RLVR via PPO; heavy model averaging; Tulu 3 released all data and code.

Post-train a small model and measure each stage

Turn a small base model into a chat model with SFT and DPO, and measure what each stage did. Pick a base that fits your hardware, such as Qwen/Qwen3-0.6B-Base or HuggingFaceTB/SmolLM2-360M on one GPU or a free Colab GPU, and use TRL.

Chapter project

Post-train a small model, end to end

Measure what SFT and DPO each changed, and whether prompt masking and length normalization mattered.

  1. Baseline. Write 30 prompts: 10 chat, 10 with checkable constraints (under 40 words, exactly 3 bullets, all lowercase), 10 grade-school math with known answers. Generate from the base model with a chat template applied and save the outputs.
  2. SFT. Train on 10k to 20k examples of trl-lib/Capybara or a slice of allenai/tulu-3-sft-mixture, twice: with and without assistant-only loss. Verify the labels on one batch with your section 02 masking code first.
  3. Decontaminate. Implement 8-gram overlap between the 30 prompts and the SFT data. Report hits and remove them.
  4. Preference data. For 1,000 to 2,000 prompts, sample 2 to 4 responses from the SFT model at temperature 0.8 to 1.0. Label pairs with an LLM judge and a short rubric, or with the section 05 verifiers (correct beats incorrect).
  5. DPO. Train with DPOTrainer using loss_type="sigmoid", beta=0.1. Repeat with loss_type="ipo" or your own dpo_norm from section 03.
  6. Evaluate. For base, SFT masked, SFT unmasked, DPO and the DPO variant: constraint pass rate, math accuracy, average length, and a blind pairwise comparison on the chat prompts.
  • Labels checked on one batch before the SFT run launches.
  • Decontamination hits reported and removed.
  • All five checkpoints scored on all four measures.
  • One-page write-up: what changed from base to SFT, whether masking mattered, whether DPO helped constraints and chat preference, whether length grew and normalization changed it.
  • Two examples where DPO made things worse, with an explanation.
